# 核验检查点保存的 Windows 临时冲突修复

本次为独立 BUG 修复。用户已批准 `app/storage/report_postwrite_runs.py`、`tests/test_report_postwrite_flow.py` 和本文档三个文件，工作树为 `C:/Users/admin/.codex/worktrees/postwrite-checkpoint-storage/survey-web`，分支 `codex/bugfix-postwrite-checkpoint-storage`，基线 `main@65144bcd418e36c812bfc0c37b2fa179a4ffd3bc`。日志筛选栏修复留在原设置工作树，两者分别验收，不在本轮整合。

## 复现与原因

原始 `RunStore.save` 完整写入临时 JSON 后只调用一次 `os.replace`，没有对 Windows 文件替换临时冲突的有限重试。原代码的 74 项报告检查中实际观察到两次 `os.replace` 的 `PermissionError / winerror 5`，其中一次使取消恢复用例的停止原因变成 `PermissionError`，测试预期的 `cancelled` 没有成立。

使用不共享删除权限的真实 Windows 读句柄，可以控制同一故障在不同检查点出现。四个此前波动用例均复现失败：未知用量后恢复停在 partial、自定义写作来源卡片为空、恢复调用记录前缀不符、取消状态变为 PermissionError。在初始登记尚未落盘时制造同一冲突，还复现了取消用例等待原意核验信号 3 秒超时。关闭句柄后同一文件能够正常保存，旧文件内容未被失败操作覆盖。

这些对照证明文件替换失败可以导致已观察到的各类症状，并已抓到实际发生的同类系统错误；具体是哪个进程持有现场冲突句柄仍未确定，不将原因写成某款杀毒软件、索引器或本平台读取造成。

诊断记录位于此前已批准的设置工作树 `.test-artifacts/settings-navigation/`：`diagnose-postwrite-observed-result.json`、`diagnose-windows-lock-result.json`、`diagnose-postwrite-controlled-lock-result.json`、`diagnose-postwrite-controlled-timeout-result.json`。控制注入中的失败是修复前定位证据，不是修复后的验收结果。

## 代码行为

- 只对替换操作的 Windows 错误 5、32、33 重试，每次 `save` 最多执行三次替换；两个退避间隔为 20ms、50ms。
- 完整序列化和写临时文件只执行一次，各次替换重用同一个临时文件。保持原子替换，不直接截断写入目标文件。
- 冻结输入校验、运行编号校验、重复创建拒绝和损坏检查点保护保持原规则；这些情况不会进入替换重试。
- 非上述 Windows 错误、临时写入磁盘错误等直接失败，不重试整个保存流程或模型任务。
- 重试耗尽继续抛出原始保存异常，旧检查点保留；临时文件清理失败单独记录提醒，不替换原异常、不把失败标为完成。
- 没有修改模型、提示词、输出上限、模型重试、调用预算、流水线成功条件、取消规则或既有测试的 3 秒等待时长。

## 日志

正常一次保存成功不新增逐检查点日志。同一次保存发生临时替换失败时，最多记录一条“正在有限重试”，随后记录恢复成功或保存失败。日志保留带时区时间、操作人姓名、阶段、尝试次数和系统/Windows 错误码。运行编号沿用通用脱敏，不输出原始 OS 异常正文、文件路径、冻结输入或模型内容。

清理失败时提示“核验临时文件暂未能清理”，保存结果保持实际状态；最终保存失败提示检查文件访问状态，并保留上一次成功保存的内容，不声称原因必然是占用或权限设置。

## 离线验收方式

| 检查 | 验证内容 |
