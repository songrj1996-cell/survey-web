## 使用流程

1. 在“群组管理 → 质量标注”建立任务，明确名称、发奖日期、基础与优秀追加奖励、重复提交规则和次数门槛。公告提取只给出附原文依据的建议；发奖日期须人工确认，手动改过的字段不会被重新提取覆盖。
2. 上传 CSV/XLSX，确认 playerid、主观题、可选次数与 ADV 列。核查所有启用名单，处理长数值 ID 精度风险、未匹配身份、同 playerid 或同 ori 的重复组；原始上传和排除记录保留。
3. 启动或重试前再次读取最新名单，失败则不进入模型队列；通过后启动后台标注。未达次数门槛直接无效且不调用模型；空值待补齐，不当作 0。质量复用既有严格逐题证据及整体判断流程。失败部分保留成功结果，仅重试缺项。人工整体调整和恢复均需说明；AI 作答由操作者确认。
4. 完整结果确认后生成一人一行任务记录。重复提交任务数据列显示反馈份数，包含无效份；非重复有门槛任务显示次数，无门槛则空白。复制为无表头 12 列 TSV 与 HTML，ori/群内状态使用当前粘贴行的查找公式。
5. 在“奖励整理”明确选择日期和已确认任务，也可导入旧 Excel 或录入独立其他奖励。读取最新名单，确认身份及账号冲突；生成前再次读取，变化会展示新旧差异并要求重新核对。
6. 生成不可变批次，下载无表头 `zoneid<TAB>uid<TAB>301-总钻石` TXT（CRLF）。同账号跨任务正常累加；重试同一生成操作、重复下载不会重复占用来源。生成 TXT 不代表已向游戏账号发奖。

4 份反馈中的 2 优秀、1 普通有效、1 无效，在基础 100、优秀追加 100 下得到基础 300、追加 200，总计 500；任务记录 H 列为 4。

## 名单连接与公式配置

- 在“名单来源”填入飞书电子表格或 wiki 链接，读取工作表列表，分别选择 Sheet 和表头行。
- 每份来源独立映射 playerid、ori、当前状态、可选昵称；在群与退群状态必须明确且不重叠。未知状态成为待处理问题，不能自动当成退群。
- 默认使用当前操作者的飞书用户授权；应用身份仅在应用已获表格访问权时可用，不借用其他成员登录凭据。业务使用名单不要求操作者有“名单来源”编辑权限。
- 读取完整范围，不采用界面可见行；分段读取需版本一致。表头、Sheet、列结构或读取权限变化时阻断，不用缓存冒充最新名单。任一启用来源失败，不返回部分名单当作完整结果。
- 同工作簿公式自动跟随映射。跨工作簿必须有已同步的目标名单 Sheet，并填写同步说明；复制前比对来源与目标的 playerid、ori、状态。无法证明同步时拒绝复制，未实现任意跨表直接引用。
- 当前测试工作簿的原“人员名单”和“member list”未改动。新建的 Discord/WhatsApp 验收 Sheet 使用不同表头行与列映射，真实 API 共读取 9 条；同一上传文件的 19 位、前导零和加号 ID 均正确匹配。
- 用户已添加本机验收回调并完成登录。既有开放平台权限为应用身份；用户将测试表授予应用可阅读后，正式名单接口已成功列出工作表并读取合成名单。没有新增开放平台权限；不要在聊天中发送 token/密钥。

## 运行限制与测量口径

| 配置 | 默认值 | 含义 |
|---|---:|---|
| `GROUP_TASK_CONCURRENCY` | 2 | 同时执行的后台质量任务 |
| `GROUP_TASK_REQUEST_CONCURRENCY` | 2 | 单任务真实模型 HTTP 请求上限 |

| `GROUP_RUN_TIMEOUT_SECONDS` | 7200 | 一轮任务从首次执行起的总预算，包含后续轮转等待 |
| `GROUP_RUN_MAX_HTTP_ATTEMPTS` | 1000 | 一轮任务上游尝试总数，重试也计数 |
| `GROUP_FEEDBACK_MAX_ROWS` | 10000 | 单次反馈行上限 |
| `FEISHU_SHEETS_READ_TIMEOUT` | 45 | 单次飞书请求超时秒数 |
| `FEISHU_SHEETS_RANGE_ROWS` | 1000 | 分段读取行数 |
| `FEISHU_SHEETS_MAX_ROWS` | 200000 | 工作表读取行上限，超限明确报错 |
| `LLM_TASK_ANNOUNCEMENT_MODEL` | 质量模型配置 | 公告提取模型；单次提取最多 2 次上游尝试、120 秒 |

这些限制只约束新后台任务，不声称限制整个模型网关、其他平台进程或已有报告调用。公告提取独立于后台队列。

每轮保存 `queue_wait_seconds`、`execution_seconds`、`save_seconds`、`http_attempts` 和安全的尝试事件。队列等待按每次轮转累加；执行为处理段墙钟时间，不将并发请求时长相加。保存耗时含锁等待、读改写、fsync 和替换，作为执行相关的子项单列，不能与执行简单相加；不包含写入这些耗时数字本身的诊断写入。服务异常中断时标记 `timing_partial`，不伪造尚未保存的耗时。
