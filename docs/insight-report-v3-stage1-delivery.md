## 1. 本阶段交付

- 建立 `insight-findings-v1` 产物契约，逐开放题保存 complete / degraded / skipped 状态。
- 模型只接触并返回调用内短 ID；代码校验后再展开为不进入模型上下文的全局来源 ID。
- 同题、同 scope 内先按玩家合并回答，`support_count` 以唯一玩家计数。
- 非开放题在 scope 选择时排除；只有开放题无有效回答时使用 skipped。
- 使用批准的频次档位做确定性下界校验；跨题只允许“多道题均有提及”，不相加人数。
- 单题首次调用后最多重试 2 次；失败题降级并保留该题全部来源 ID，不阻断其他题。
- 默认 20 分钟只告警不中止；只有隔离 CLI 显式参数可启用硬超时。
- CLI 自动路径直接调用现有上传、列识别、列确认、方案规划、方案确认和统计服务；人工路径复用
  已完成前四步的 session。两条路径进入同一个阶段一函数和同一产物 schema。
- 同步 main 的题型与画像用途拆分后，CLI 不再改写任何列的 `role`；自动确认原样传递
  `role`、`use_as_profile` 和 `profile_scope`，分支题与画像用途由生产服务统一解释。

V3 阶段一没有对同步后的 `survey_stats.py` 增加额外修改，不接入正式报告写作与 UI，不实现阶段二、三。

## 2. 真实模型回放

三份 XLSX 均通过公司 LLM 分发服务运行。原文只保存在隔离 session 的来源注册表；下列 evidence
不重复写出原文。

本轮验收数据对应的档位表版本标记为 `frequency-v2-main1416376-2026-09-23`，提示词版本标记为
`findings-prompt-v2-frequency-rules`。这两个名称是本交付报告使用的版本标签，当前阶段一产物 schema
尚未单独保存它们。v2 规则包含：

- “部分”的代表样本下界由 2 提高为 3；
- “大量/很多”的人数下界改为 `max(6, ceil(N × 20%))`，代表样本下界为 5；
- 当小样本下相邻档位的代码可验证条件碰撞时，保留较弱档位、禁用碰撞的较强档位。

以下 2.2 为当前验收结果。此前 `55 / 0 / 0`、359.50 秒和 591,831 tokens 对应旧档位表及旧
`<frequency_rules>` 提示词；同步 main 前的 v2 回放为 397.57 秒和 692,626 tokens。两组都只作为
历史对照，不再作为当前验收数据。

### 2.3 真实运行中发现并修复的问题

1. 最初 6 题试跑中 2 题因模型不知道当前 N 对应的精确档位下界而降级。提示词改为由代码注入
   当前题的精确整数下界后，同一 6 题在并发 2、4、6 下均为 6/6 complete。
2. 最初打野自动准备中，旧字段把题型和画像用途耦合，CLI 曾临时把分支父题从 `profile_dim`
   改成 `single_choice`。`main@1416376` 已将题型与画像用途拆分；临时改型现已删除，三份 XLSX
   原样确认字段后均完成自动前四步与阶段一。
3. 早期诊断没有把最终降级题的失败尝试计入汇总。现已统一记录所有逻辑调用和上游尝试，并由
   测试守住。
4. Review 发现旧档位表在小样本下存在“部分”与“少数”代表样本下界相同，以及“绝大多数”与
   “大量”人数下界重合或语义倒置的问题。v2 提高“部分”的代表样本下界，改用比例型“大量”
   下界，并通过 availability 禁用碰撞的较强档位；N=10/20/40/60/95/172 的参数化测试守住严格
   单调和相邻档位可区分。

这些失败均发生在隔离验证目录；主工作树 `data/` 未读写。

## 3. 历史 v1 随机 5 条 finding 人工计数核对

本节对应 `frequency-v1` 旧 prompt，保留用于说明档位修正来源，不作为 v2 prompt 的抽样结果。
抽样总体为旧三份全量产物的 467 条 finding，固定随机种子为 `20260922`。人工按 finding 的语义
逐条回看该题 scope 内全部玩家原文，以唯一玩家重新计数。以下“偏差”为“模型 support_count -
人工计数”。报告不记录原文或玩家身份；本轮 v2 验收未要求重新进行人工语义抽样。

| 数据 / finding | N | 模型计数 | 人工计数 | 偏差 | 人工判定口径 |
|---|---:|---:|---:|---:|---|
| 打野 `18/f6` | 27 | 3 | 6 | -3 | 明确表示落后后难追回、难以恢复等级/经济或近乎无力反制 |
| 战备重构 `40/f4` | 90 | 7 | 6 | +1 | 明确认为 Skill Layout 与既有界面设置重复，或不适合放在指南中 |
| 金币路 `18/f5` | 62 | 13 | 13 | 0 | 作为己方常用英雄提到 Granger，并说明选择或使用原因；仅作为对手提及不计 |
| 战备重构 `22/f5` | 90 | 3 | 2 | +1 | 明确要求英雄搜索或表情筛选；只抱怨列表间距、不提出该功能不计 |
| 金币路 `12/f6` | 14 | 1 | 1 | 0 | 明确表示想玩发育路的人多、位置竞争大 |

结果：2/5 完全一致；平均绝对偏差 1.0 人；最大绝对偏差 3 人；平均有符号偏差 -0.2 人。

这组样本未发现数量级夸大，但也证明 `support_count` 不是确定性精确计数。阶段一只能定位为
“证据绑定 + 防明显夸大”，不能定位为“保证无杜撰”或“精确统计”。

## 5. 质量与速度风险复核

报告质量：

- 必然存在：`support_count` 是模型估计，不是代码逐条语义分类后的精确人数。
- 本次已发生：5 条抽查中 3 条有 1–3 人偏差；模型既有高估也有低估。
- 已缓解：来源身份、题目归属、代表玩家下界、频次档位下界和最大 N 均由代码校验；模型不能
  输出原文或全局 ID；单题失败不污染其他题。
- 仍待后续：语义曲解与跨题写作质量要由阶段二写作和阶段三审校验证。

生成速度：

- 特定条件下必然发生：开放题越多、文本越长，调用数和 token 线性增加；每题重试会增加耗时。
- 本次 main 同步后 v2 实测：55 个 scope 的阶段一合计 530.64 秒、56 次逻辑调用、65 次上游尝试、
  712,011 tokens；包含自动前四步的 CLI 总耗时为 786.67 秒。旧 v1 固定 6 题试跑中并发 4 比
  并发 2 快 36%，而并发 6 没有进一步收益并增加一次上游尝试；该并发结论尚未在 v2 的 20 题
  规模复验。
- 默认行为：仍使用并发 2；超过 20 分钟只告警，不中止。隔离试验可显式选择并发和硬超时。
