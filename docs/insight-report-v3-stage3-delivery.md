## 1. 本阶段实现

### 1.1 证据绑定的语义审校

- 审校模型只看本批短 claim ID（`c001`）和短 source ID（`r001`），不看、不输出全局来源 ID、
  玩家身份或画像。正文 block 与其 findings 的全部代表来源核对；证据要点与其唯一来源核对。
- 证据要点有问题时清空概括，正文确定性回退为“详见 E-xxx”，完整译文仍在证据附录。正文 block
  有问题时最多进行一次合并定向修复，再经过既有频次、画像、数字与 Markdown 门禁，并独立复审一次。
- 每个单元必须落入 `passed / evidence_fallback / repaired / needs_review / incomplete` 之一。
  `needs_review` 与 `incomplete` 会在 H1 后逐项列出，并通过 SSE 提示；不会伪装成审校通过，也不会
  因局部失败丢弃整份报告。
- 默认审校模型为 `gpt-5.6-terra`，fallback 为 `gpt-5.6-sol`，reasoning 为 `high`，输出上限为
  12,000 tokens。超过 300 秒只告警，不中止报告。

### 1.2 动态全覆盖容量

- 初审不再固定最多 2 批，而是按全部计划单元的序列化体积动态拆分，直到所有单元取得终态。
- 90,000 字符是常规装箱目标，不是跳过阈值；每批另设 24 个单元上限。单个单元连同全部绑定来源
  超过目标时，隔离为独占批次照常调用，不删来源、不静默跳过；只有真实调用失败才记为
  `incomplete`。
- 初审、定向修复和修复复审均使用同一有界并发执行器，默认并发 4，可配置为 1—8。结果按原计划
  顺序归位，异步完成顺序不会改变报告顺序。
- 初审发现的全部正文问题都会进入动态修复批次；通过代码门禁的全部修复都会进入动态复审。每个
  正文 block 仍然最多修复一次、复审一次，不因增加容量而无限迭代。
- 诊断新增各阶段批次数、计划／已审单元数、终态分布、实际峰值并发、逐调用输入字符、超目标调用、
  按阶段归属的上游失败、逻辑调用数和上游尝试数。

### 1.3 其它阶段三机制

- 回放后自动扫描“数量／比例／普遍性词 + 玩家／受访者主体”的宽泛模式，只输出待人工确认候选，
  不自动改文、不自动加入黑名单。本轮三份最终回放候选数为 20 / 8 / 0。
- `validation_plan` 已含验证、核验、评估、监测等验证语义时，确定性装配不再重复追加“来验证这一
  方向是否有效”。
- 玩家主动填写的游戏账号标识按已确认的内部核对与追溯用途原样保留。它不是本次新增暴露面，
  不新增脱敏规则，原交付中的对应 NO-GO 已解除。

## 4. 质量与速度负面影响复核

### 报告质量

- **本次必然发生且已观测**：所有模型生成审校单元都接受初审，原先 55%—77% 未审的结构性缺口已
  消除；最终只留下 1—5 个具名问题，达到人工可逐条复核的量级。
- **本次已观测**：三份最终回放共触发 37 个证据要点安全回退、19 个正文修复后通过，并保留 8 个
  待人工复核项；说明全覆盖不是只增加调用，也实际拦住了语义问题。
- **特定条件下必然发生**：单个审校单元超过装箱目标时仍会把全部绑定来源发送给模型，单次上下文
  负担和失败风险高于普通批次；失败会显式标为 `incomplete`，不会静默通过。
- **可能发生**：宽泛频次扫描存在高召回误报。本轮只输出候选，不自动改文，因此不会直接损伤正文，
  但候选仍需人工确认。
- **证据不足，无法判断**：最终三份没有真实触发超目标独占调用，无法据此保证外部服务对任意超过
  90,000 字符的单单元都能成功返回。

### 生成速度与成本

- **必然发生**：动态全覆盖把审校逻辑调用从固定最多 4 次提高到本轮 9 / 12 / 10 次；审校耗时为
  255.967 / 147.757 / 135.950 秒，并增加相应 token 与外部服务费用。
- **特定条件下必然发生**：初审发现正文问题时增加一次修复和一次复审；报告更长、绑定来源更多时，
  批次数与输入 token 随之增加。
- **可能发生**：默认并发 4 会提高同一时段的上游压力。战备出现 3 次流式错误并被重试吸收，但其
  输入只有 76,259 字符，现有证据不能把错误归因于输入长度或并发，也不能证明二者无关。
- 三份报告总耗时均低于 17 分钟。与旧回放相比，金币路增加约 78 秒，打野减少约 117 秒，战备减少
  约 159 秒；因章节数、输出长度、重试和模型随机性不同，不能把差值硬归因于并发或容量改造。
