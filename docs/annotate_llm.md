# 数据标注：直连 LLM 架构

数据标注不再调用 Dify Workflow。后端在
`app/services/annotate_workflow.py` 中编排三个独立任务，统一通过
`app/integrations/llm_client.py` 调用公司 LLM 分发服务：

- AI 作答识别
- 逐题质量打标与整体综合判断（同一次调用）
- 统一中文翻译

原来两个 Dify DSL 中相同的 `translation_repair` 分支已合并为统一翻译任务；
AI 作答识别和质量打标仍保持各自独立的业务口径与输出结构。

## 标注流程

```text
上传问卷回收表
  → 本地解析、识别候选列
  → 统一翻译非中文表头并由用户确认列
  → AI 作答识别：按玩家综合全部主观题回答
  → 人工确认疑似 AI 作答结果
  → 质量判断：逐题无效 / 有效 / 优秀 / N/A，同时独立判断整体质量
  → 统一补齐非中文回答的中文翻译
  → 本地校验完整性、导出 Excel 并写入历史
```

翻译任务同时服务于表头翻译和回答翻译。中文原文、纯数字和无需翻译的游戏术语
由本地规则直接保留；模型只处理仍缺失的非中文内容。

## 三个模型任务

| 任务 | 主要输入 | 主要输出 | 默认首选 | 默认备选 | 推理强度 | 输出上限 |
|---|---|---|---|---|---|---|
| AI 作答识别 | 同一玩家的全部主观题回答 | `ai_prob`、`polish_prob`、中文理由、正反证据原文 | `gpt-5.6-sol` | `claude-sonnet-5` | `high` | 32K |
| 质量打标 | 玩家 ID、全部已选主观题题干与完整回答、自动识别的表内参考答案、可选调研背景 | 每题标签、中文理由和连续原文证据，独立的整体标签及理由 | `gpt-5.6-terra` | `claude-sonnet-5` | `medium` | 32K |
| 统一中文翻译 | `id`、单元格 `key` 与原文 | 对应 `id` / `key` 的完整中文译文 | `gpt-5.6-terra` | `gemini-3.5-flash` | `medium` | 16K |

模型配置复用 `LLM_API_BASE` 和 `LLM_API_KEY`，并可分别通过以下环境变量覆盖：

- `LLM_ANNOTATE_AI_MODEL` / `LLM_ANNOTATE_AI_FALLBACK_MODELS`
- `LLM_ANNOTATE_QUALITY_MODEL` / `LLM_ANNOTATE_QUALITY_FALLBACK_MODELS`
- `LLM_ANNOTATE_TRANSLATION_MODEL` / `LLM_ANNOTATE_TRANSLATION_FALLBACK_MODELS`
- 三个任务各自的 `*_REASONING` 和 `*_MAX_TOKENS`

完整示例见项目根目录的 `.env.example`。迁移后不再需要
`DIFY_AI_DETECT_KEY`、`DIFY_QUALITY_KEY` 或通用 Dify 配置。

## 调研背景与题目条件

配置页的“调研背景说明”同时适用于 AI 识别和质量打标，任一任务勾选时均可填写。
可补充已知的题目用途、前置评分与跳题条件，例如明确哪道题仅向低评分玩家展示，用于追问
不满意原因。背景只帮助理解题意，不作为玩家回答或原文证据，不能用来指定标签、改变分级
规则或输出格式；未提供的实际评分、玩家经历和跳题条件不得猜测。

质量打标将背景与题干、完整回答放入同一次请求，不新增背景分析调用。首次调用、缺项修复、
仅补整体和拆批预算均使用会话中保存的同一背景；留空或旧会话没有此字段时保持原行为。
背景增加输入长度，超过单批预算时可能增加批次和耗时；单名玩家连同背景超过预算时按既有
规则保留未完成状态，不截断原文或背景后勉强生成结果。

质量输入会根据未选主观题列的原始表头，保守识别明确的评分、选择和经历等参考列，并以
`context_answers` 中的 `key`、`question`、`answer` 提供当前玩家的原题与原值。ID、联系信息、
不相关人口属性、标注标签/理由/证据/翻译等衍生列不作为参考输入；未选开放叙述题不能仅因
回答短或重复少就当作选择题。识别不依赖额外模型调用，也不要求研究员逐次填写背景。

参考列只帮助理解题意，不参与质量分档、不作为主观回答证据；不能因为玩家身份、段位或
使用经历直接加减等级，也不能把不同题目的评分错误套到当前回答。参考答案与主观原文在
首次、缺项修复、仅补整体及输入预算计算中使用同一路径，不截断答案来容纳参考信息。

表头规则可能漏掉表达不明确的参考列；此能力不等于自动理解整份问卷，也不能读取问卷后台
未导出的跳题设置。原表缺失评分或条件时不得恢复、推断或补造。可选背景仍只填写已知且
适用范围明确的事实；修改背景后应重新配置并重跑，不会追溯改写历史结果。

## 批处理与完整性

- 保留 AI 识别 45K、质量打标 40K 的单次输入字符预算。
- 保留按行数和字符数拆批、并发上限及 SSE 心跳，长任务期间前端会持续收到进度。
- AI 识别以玩家为单位综合判断，`ai_prob` 与 `polish_prob` 相互独立；仅使用 AI
  润色不等同于实质内容由 AI 生成。
- 质量判断按题干的实际要求判断完整性：原因题给出明确原因即可有效，不强求实例、影响或建议；
  条件题单纯回答“没有问题”为有效，不自动优秀。优秀要求充分、具体且有价值的说明。
- 长短、字数、句数及原因数量均不是逐题分档标准。原因可以是实际使用结果、信息或功能是否
  满足需要等可理解依据；不继续追问设计机制、技术根因或完整过程。只有评价结论而没有依据
  时仍无效。“请详细解释”不能把优秀的展开程度变成普通的最低门槛。
- 纯否定答复与否定后补充实质内容须分开：`no_issue` 仅指全文没有另外提供实质信息；有补充
  体验、依据或建议时按全文评估 `substantive` 及档位，不能只看开头“没有问题”就封顶普通。
  “是否有问题，若有请说”和“请描述不满的地方/为什么不满意”按各自实际要求理解，不能
  自行把明确要求描述不满的题目改成否定分支，也不能补造未提供的评分和条件。
- 先区分题目需要的动机、体验、具体困难或操作信息。仅提到相关话题或抽象能力要求，未必
  已回答实际困难；简短但可理解的退出动机仍可有效，不要求继续解释原因的原因。
- 影响因素题须能理解因素的具体所指；具体条件、行为、状态或关系已是实质信息，不另要求
  影响结果、正负方向或机制。孤立对象名词未说明具体所指仍无效。题干明确另外要求解释结果
  或原因时才核对该项要求，不自行追加。真正只问名称或列举项目时名称清单可足够，不能混用
  两种题意；判断不依据词数，影响因素题仍用 `explanation` 核对最低信息。
- 多个独立分问已有可独立成立的实质回答、但遗漏另一实质部分时可普通，不能优秀；不按分问
  数量或覆盖百分比裁决。评价及其所求原因属于同一判断，只有评价而没有依据仍无效。
  `q_checks.support=substantive` 表示已提供最低可用的实质信息，不代表每个分问全部作答。
- 时间、版本、场景、新旧比较或多个理由不自动构成优秀；须看这些信息实际解释了什么。
  不统一设置字数、实例数量或必须描述根因的门槛，普通/优秀的合理边界仍需真实样本复核。
- 交互反馈已充分说明具体操作、当前与期望行为的差别或体验价值时，可以优秀；不继续强求
  额外实例、技术原因或所有信息要素齐全。建议数量不是门槛，一条充分具体的建议可以优秀，
  多条简短建议也不会自动优秀。
- 正向体验、使用习惯和设计取舍与问题反馈同等评优：具体说明功能与使用价值的关系，也可优秀，
  不以交互改进为所有优秀回答的必选条件。分档前须核对全文，不能遗漏态度句后的实质说明。
- 相似或重复表述不等于跨题无关。判断相关性须结合当前题干、具体对象及已提供的指代依据，
  不能因前题出现过同类子菜单问题，就断言当前回答只属于前题功能。“同上”也不自动有效：
  只有能够明确解析指代且确实回应当前题意时，才按实际内容判断；不能补造模块归属或缺失细节。
- 标签与理由必须一致。判为普通时，理由应解释为什么具体信息仍不足以优秀；已经认可完整、
  具体的交互差异和体验价值时，不能再仅以缺少额外信息为由降档。不得为凑齐理由改写原意。
- 理由应简明指出实际答到或缺少的题意内容，不能仅复述标签，也不能把玩家只提到某个背景
  描述为已经解释了过程、影响或因果关系。引文来自原文不代表它足以支撑该档判断。
- 整体由模型阅读同一玩家全部已选主观回答后独立判断，不按逐题标签折分、均分或比例决定。
  后端的低投入组合规则不再覆盖新版整体结果；全部主观题确实为空时，逐题固定 N/A、整体无效。
- 正常质量调用同时返回逐题和整体，不新增独立整体调用；新增输出和判断工作可能增加耗时、
  费用或输出截断风险，实际语义质量与速度需要真实模型回放验证。
- 质量输入按完整玩家拆批，不截断回答。如果单个玩家全文仍超过当前输入预算，明确保留
  未完成状态及原因，不使用残缺输入生成整体结论。AI 识别和翻译原有输入处理保持原行为。
- 每位玩家的质量输入以 JSON 将题号、题干与原文逐项绑定，保留换行、竖线等原始字符，
  避免横向宽表弱化题答对应关系。整体仍读取该玩家全部已选题；补跑仅请求缺项，完整上下文保留。
  每位玩家重复携带题干可能增加输入长度，超预算时仍按完整玩家拆批，实际批数与耗时需回放验证。
- AI 结果、质量结果和翻译结果分别记录缺失集合，避免一个阶段的缺失被误报为另一个阶段失败。
- AI 识别按缺失玩家补跑。质量结果按缺失题目与缺失整体分别记录；部分可信结果保留供补跑。
  补跑仍提供该玩家全部主观回答，只要求输出缺失项，不能替换已有整体、成功题或人工改标。
- 翻译先按每批 20 项处理，缺失项再按每批 5 项补跑；超过单次字符预算的长文本会分段翻译后合并。

## 输出校验与降级

- AI 识别校验玩家 ID 是否与输入唯一匹配、概率整数范围、理由，以及证据是否为回答中的连续原文。
- 质量打标校验每个玩家和每道题是否完整，标签只能是“无效反馈”、
  “有效反馈”（兼容“普通反馈”）、“优秀反馈”或 `N/A`，证据必须来自对应单元格。
- 新生成结果采用独立的 `quality_check_policy_version=1`，在同一次质量调用内返回逐题
  `q_checks[key]={requirement,support}`。`requirement` 为 `direct_answer`（直接回答）、
  `explanation`（解释或展开）、`specific_description`（实际问题或体验）、`steps`（主要路径）
  或 `conditional`（有问题才需说明）；`support` 为 `answer`（结论）、`substantive`（所需
  实际信息）、`no_issue`（明确无问题）或 `none`（未提供可理解的相关内容）。
- 完成最低要求的组合：直接题可配结论、实际信息或无问题；条件题可配实际信息或无问题；
  解释、描述、步骤题须配实际信息。完成后才能有效或优秀，未完成只能无效，单纯无问题不能
  优秀。代码检查的是模型声明与标签是否自洽，不会自动替模型改标签。
- 新协议的每道非空回答还必须有同题的非空连续原文引用，不合法时不得通过回填整段原文
  伪装成通过。真正空答本地生成 N/A，不要求检查字段或证据。`q_reasons` 说明实际最低要求
  和原文答到或缺少的内容；不能以有引文、出现专业术语或与题目相关代替最低要求是否满足。
- 缺检查、坏枚举、标签自相矛盾或引用错题，均只补受影响题目；保留已完成题和独立整体，
  不扩大现有两轮质量补判上限。必答检查本身不新增首次调用，但输出字段必然增多；触发补判时
  会增加调用和等待。重复失败保持技术待补，不自动生成可导出的标签。
- 检查不能证明语义正确：模型仍可能把泛泛评价误报成实质说明，或误判题目要求。没有字数
  门槛，也没有按特定调研、单元格或关键词硬改标签；必须用真实样本评估漏判和误伤。
- 整体必须有合法标签与非空中文理由，不能为 N/A；缺失整体不能回退旧算分、默认无效或当作完成。
  新版来源和策略版本由服务端赋值，模型不能自报可信来源。字段完整不代表语义判断已经正确。
- 新生成质量结果采用 `quality_reason_policy_version=1`：理由必须为有效字符串，拒绝空白、
  仅复述档位或明确占位内容，不将 null、数组等转换为非空文字冒充理由。校验和缺项恢复使用
  同一标准；这只能拦截明确的输出问题，不能确定性证明观点充分、理由忠实或标签正确。
- 逐题理由还会与该题原文是否为空做硬性对照：原文非空时，拒绝“回答为空”“该题未作答”
  “未提供回答”等明确空答断言。首次校验、缺项识别和补跑合并使用同一检查；真正空题仍由本地
  生成 N/A。“界面有空白”“未解释原因”、正常的“没有问题”或引用/否定空答说法，不据此判错。
  该检查针对明确的文本断言，不等于程序能理解所有同义表达或检查全部语义事实。
- 不合格理由由现有有界缺项机制补跑，该题标签、理由和证据可能一起重判；已合格题目和
  已完成整体保留。异常修复可能增加调用和耗时，不保证只改理由或固定只多一次调用。
  补跑仍返回矛盾理由时保留待补状态，不把该题包装为已完成，也不由程序编造替代理由。
- 翻译校验 `id` / `key` 是否与请求一致、译文是否非空，并保留无需翻译的中文或术语内容。
- JSON 无法解析时会先让同一模型按原任务定向再生成一次；模型调用失败或再次无效时，
  再按任务切换到备选模型。仍缺失的结果保留明确状态，供补跑和前端提示使用。
- 翻译缺失不会删除已经通过校验的 AI 识别或质量标签；导出只使用可信结果，
  不会用不完整的模型输出覆盖已有有效标注。

## 人工复核与旧结果

### 新判无效的模型复核

- 新模型输出中，通过结构校验但初判为无效的题，先暂存在服务端 `q_invalid_reviews`，
  不立即写入可导出的逐题标签。普通、优秀及独立整体仍按原流程保留。
- 原有两轮结构补缺不会再次初判这些候选；随后仅对候选执行一个有界的模型复核阶段。
  输入仍包含该玩家完整题干、原文和表内背景，另附待审核的初判理由；初判是待分析数据，
  不是人工结论或必须服从的指令。每位玩家合并为一个对象，防止多题拆成重复 ID。
- 复核检查初判是否追加了题目未要求的机制、实例、完整过程或额外总体态度句。
  通过最低要求的候选纠正为有效；仍缺必答内容的维持无效。复核不重新区分普通与优秀，
  因此纠正为有效仅表示普通，潜在优秀仍可能被低估；原先已经有效的题及整体不受这一阶段改写。
- 复核只能原子更新目标题的标签、理由、同题连续原文证据和检查项；不能修改其他题、翻译、
  整体或人工复核记录。确认结果仍须通过原有结构和原文引用校验。
- 异常、超时、漏返、重复 ID 或不合法引用，保持候选待处理，不自动保留初判无效，也不默认普通。
  缺题识别、导出门禁及续跑共享这个状态；取消或重试保留已成功题和整体，候选仅重做复核。
- 完整旧结果和已有人工改标不追溯调用；只有新生成或新补判的无效候选进入此阶段。
  该流程是后台模型复核；下述信心元数据供独立人工复核界面后续接入。
- 没有新无效候选时不增加调用；有候选时必然增加逻辑调用和输入输出量，具体耗时取决于候选分组及服务响应。
  “一轮复核”不等于一次 HTTP 请求：保留有界 JSON 重试及模型备选，每次 completion 限制一个真实 HTTP 尝试。
  每个质量批次的整段复核由 `ANNOTATE_QUALITY_INVALID_REVIEW_TIMEOUT_SECONDS` 限时，默认 180 秒。
  超预算不截断原文，保留待处理；持续失败不会在同一阶段无限重试。
- 服务端记录复核耗时、逻辑调用、真实上游尝试、候选完成/待处理数量、备选模型及停止原因。
  额外复核仍可能误放真实无效，不能代替人工标准；需同时回测无效准确率、召回率及待处理数量。

- 新版人工改单题只更新该题及复核记录，不调用模型，不再折算整体。整体原始结论和理由保留，
  页面与重新导出的 Excel 明确说明整体独立判断、逐题人工调整未重新评估整体。
- `quality_policy_version=5` 标识新版，`overall_source` 区分模型综合判断与全题空白的本地处理。
  没有新版标记的旧结果继续说明旧规则来源，不能包装成新模型结果。
- 历史归档 Excel 原样下载，不迁移、不重算。旧完整会话仍可按旧口径复核；
  旧结果仅缺翻译时允许补译，旧质量尚未完整时提示重新上传按新口径整批运行，原结果不丢弃。
- 没有新理由规范标记的既有缓存保留原有非空理由完整性口径，不因升级自动变成待补或触发
  模型重判。新生成或明确重跑的结果执行严格理由校验；服务端标记不能由模型自报绕过。
- 没有必答检查标记的既有可信题保持兼容，不整体升级历史缓存；旧结果的新补判题必须通过
  新检查，随后按该题的 `q_checks` 严格验证。模型不能提供服务端版本或人工复核字段。
- `q_checks` 记录 AI 原判断依据。服务器记录的人工改标与 AI baseline 对应时，按 AI 原标签
  检查自洽性，保留人工最终标签及原检查；恢复原判也不删除检查。人工改标不豁免结构和引用
  来源检查，不触发模型调用或整体折分。人工复核界面、确认状态及持久化仍由独立功能任务负责。

### 逐题有效性信心与前端消费契约

信心只表示模型对“有效还是无效”的判断把握，不是答案信息量、普通与优秀的区分，
也不是经过校准的正确概率。明确缺少必答信息可以是高信心无效，简短且点题可以是
高信心普通；不使用字数、原因数量或是否举例生成复核队列。

初判、现有结构补缺和现有无效候选复核，在同一次请求中可附带：

```json
{
  "q_validity_confidence": {
    "col_2": {
      "level": "low",
      "reason_codes": ["valid_invalid_boundary"],
      "reason": "给出了评价，但是否已提供题干要求的解释存在两种合理判断。"
    }
  }
}
```

- `level` 为 `high / medium / low`；缺失或格式不合法由服务端规范为 `unknown`。
- 模型原因代码只允许 `valid_invalid_boundary / ambiguous_question / ambiguous_answer / missing_context`。
  中、低信心必须有合法非空原因代码和具体原因；否则记为未记录，不丢弃质量标签。
- 信心只输出本次目标题，与质量四字段一起按题合并。它不参与标签完成、缺题、导出门禁；
  仅缺信心不会重跑质量、补信心或增加模型调用。完整旧结果不会因此批量重判。
- 无效候选初判的信心只存入 `q_invalid_reviews[key].candidate.validity_confidence`，
  不提前用作最终标签信心。候选复核输入不附初判信心，避免这一自评分影响第二次判断。
- 复核完成后记录最终模型信心，初判与复核在有效性上的分歧另由服务端保留。
  即使最终模型自报高信心，也不能抹掉初判无效、复核改普通的分歧信号。

当前 session 的 `quality_results` 及现有 `quality_done.results` 中，每个选择题列另外带
服务端生成的 `q_review_signals[col_N]`。前端应消费此字段，不能把模型自评当人工已复核状态：

```json
{
  "schema_version": 1,
  "policy_version": 1,
  "validity_confidence": "low",
  "review_recommended": true,
  "review_focus": "validity",
  "reason_codes": ["valid_invalid_boundary"],
  "reason": "给出了评价，但是否已解释评分原因存在边界。",
  "source": "quality_assessment",
  "applicable": true,
  "assessed_label": "有效反馈"
}
```

- `review_recommended` 仅由服务器决定：低信心，或完成的初判/模型复核存在有效性分歧。
  分歧原因代码为 `initial_review_disagreement`，模型不能伪造此服务器字段。
  普通和优秀也可低信心送审；中信心保留供二级筛选，不默认进入优先队列。
- `source` 为 `quality_assessment / invalid_review / not_recorded / pending_quality / not_applicable`。
  `unknown` 不能默认显示为高信心，也不能当成模型已判断的低信心；旧数据不自动全部变待办。
- 空答 N/A 为 `applicable=false`，不推荐复核；质量未完成为技术待补齐，不能冒充人工复核项目。
- `assessed_label` 绑定模型原判；人工改标保留模型信心与依据。人工是否确认、最终标签、
  操作记录与结果版本需独立保存，不能从 `review_recommended` 推断人工是否已经处理。
- 补缺、重试及续跑只更新本次新成功的目标题，已完成题、整体、翻译和人工记录保持原有保护。

本次只交付信心生产方与现有结果接口的元数据。标注 session 仍是内存会话，历史主要为
Excel 及概要，不声称已支持重启恢复、历史复核页、逐题信心导出或人工确认事件的持久化。
缺失信心不会由答案长短、理由关键词或人工金标补造。

不会新增独立信心请求或信心补缺循环；协议文本必然变长，模型返回字段时输出量也会增加。
新增输出要求可能造成标签漂移、截断或 JSON 格式失败，进而增加现有重试和耗时。
需用冻结题干和原文对照标签、复核推荐数量、信心缺失、请求量及耗时；低信心原因仍需语义核验。
已经校准过且不存在明确剩余错误的样本，不能用来证明低信心对未来错误具有可靠检出率。

## 提示词管理

三套 System Prompt 的默认值来自迁移时提供的两个 DSL：

- `web-回答打标-AI识别-mode路由.yml`
- `web-回答打标-质量识别-mode路由.yml`

管理员可在设置页分别编辑“AI 作答识别”“逐题质量打标”和“统一中文翻译”提示词，
对应内部键为 `annotate_ai_system`、`annotate_quality_system` 和
`annotate_translation_system`。修改后的下一次标注调用立即生效，无需重启服务。

质量默认提示词正文版本为 12，明确按信息是否满足题意分档，撤去可能被误解为字数、句数或
单一原因不能优秀的描述；已有可理解依据达到普通，实质说明充分可优秀。`no_issue` 仅限全文
无其它实质信息的否定答复，已有具体体验不因开头“没有问题”降档。
条件分支、原因、动机、实际困难及主要操作路径仍分别核对，整体仍独立综合判断。
表内 `context_answers` 仅作事实参考，不猜测缺失评分或跳题条件。
正文版本用于提示词默认值迁移，与整体结果协议的 `quality_policy_version=5` 和新理由校验的
`quality_reason_policy_version=1`、必答检查的 `quality_check_policy_version=1` 不同；
本次校准不改变整体综合判断方式或历史结果来源。
版本迁移仅替换没有自定义历史的旧默认正文，包括版本 4 至 11；人工自定义正文与历史保留。
本次完整观点、影响因素与独立分问的边界也在初评和无效复核的程序维护协议中共同应用，
自定义正文仍受这些边界及必答检查、引用、整体字段要求约束；其它默认正文的语义校准不会覆盖自定义内容。
协议不增加专门模型调用或改变 JSON 字段；输入提示词增加，实际耗时、重试和语义影响须用真实模型回放核实。
开发与验证不直接编辑真实 `data/prompts.json`。
