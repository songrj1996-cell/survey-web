# 观点洞察报告 v3 开发规范

- 状态：阶段一实现与自动路径真实回放完成；人工前四步 session 复跑待最终验收
- 分支：`codex/feature-insight-report-v3`
- 基线：`main@ce3d9fa`

本文是观点洞察报告 v3 的开发依据。原始讨论稿中与本文冲突的内容，以本文为准。

阶段一实现与验证结果见 [阶段一交付报告](insight-report-v3-stage1-delivery.md)。

## 1. 目标与边界

现有 `report_mode == "insight"` 的正文生成存在三类问题：

1. 主题提取、合并、逐条分类、跨题归纳和分章写作调用多且整体耗时长。
2. 分批主题流程中的局部失败可能阻断整份报告。
3. 报告按问卷 Part 切章并重复展示统一证据表，不符合目标报告的研究主线。

V3 的目标是让证据校验成本与报告实际引用量相关，而不是与全部回答数和全部主题数相乘。
时间是需要记录和优化的指标，不是中止报告的理由。

阶段一的质量定位是：

> 证据绑定 + 防明显夸大。

阶段一不能保证“无 AI 杜撰”。它能确定性保证引用身份存在、归属当前题、频次档位满足代码
下界，并阻止模型直接输出原文；`support_count` 仍是模型对唯一玩家数的估计，必须通过真实材料
抽查评估偏差。语义曲解由阶段三审校继续处理。

## 2. 不可违反的红线

### 2.1 模型不得输出原文

- 模型输出契约中不得有 `quote`、`text`、`excerpt`、`snippet`、`original`、
  `source_text`、`translation` 等承载原文的字段。
- 模型只输出当前一次调用内的短 ID。
- 原文、全局来源 ID 和玩家身份均由代码本地管理。
- 禁止让模型复制长 ID 或原文后再做字符串匹配。

### 2.2 局部失败不得阻断其他题

- 单题失败只降级该题。
- 单章失败只影响该章。
- 审校未解决的问题标注后交付，不丢弃报告。
- 已完成题必须增量保存，后续题失败不能使其作废。

### 2.3 前四步旧行为保持不变

上传、列识别、方案规划、统计的现有生产调用路径和默认输出保持不变。阶段一 CLI 必须直接调用
这些现有 service 函数，不实现第二套列识别、规划或统计。

当前 V3 不修改 `survey_stats.py`。来源身份使用完整文件哈希、冻结方案指纹、原始开放题列表的
确定性顺序和玩家键生成。若未来必须增加行号，只允许新增 V3 显式开启的 keyword-only 来源
元数据；默认调用行为和输出必须由深度相等测试守住。

### 2.4 真实数据隔离

- 主工作树 `data/` 不得读写。
- 自动 CLI 在显式 `runtime-root` 下创建独立 `data/` 与 session。
- 人工验收可在 V3 工作树自己的隔离 session 中完成。
- 验证证据不得重复写出原始回答；原文只留在隔离 session 来源注册表。

## 3. 阶段一跨阶段契约

### 3.1 双层来源 ID

模型只看到并输出现有 `report_engine._response_ref` 生成的短 ID：`r0001`、`r0002`……

代码为每列完整开放题列表构造全局来源 ID：

```text
ir3v1-{file16}-c{column_index}-i{source_index}-p{respondent12}
```

- `file16`：文件 SHA-256 前 16 位。
- `column_index`：原始零基列号。
- `source_index`：该列完整 `open_text` 列表中的一基确定性位置，不是批次位置。
- `respondent12`：文件哈希与 `respondent_key` 联合 SHA-256 的前 12 位。
- 完整文件哈希、plan 指纹和来源注册表指纹保存在 `source_binding` 中。

全局 ID 不进入模型上下文。代码现场维护 `短 ID -> 一个或多个全局来源 ID` 映射，校验模型
短 ID 后再展开并写入 finding。阶段二只按来源注册表精确回填，不解析 ID 猜测原文。

### 3.2 玩家级预合并

同一题、同一 scope 内，代码先按 `respondent_key` 合并同一玩家的多条文本，再分配一个短 ID。
因此模型看到的每个短 ID 代表一名玩家。玩家哈希和明文身份均不进入模型上下文。

非开放题在 scope 选择阶段直接排除，不进入 `questions`。只有开放题没有有效回答时才使用
`status = "skipped"`。

### 3.3 `support_count` 口径

- `N` 是当前题和 scope 内有效回答的唯一玩家数。
- `support_count` 是模型估计的支持该 finding 的唯一玩家数。
- 代表样本最小数也按唯一玩家计算。
- 比例下界统一向上取整。
- 必须满足：`唯一代表玩家数 <= support_count <= N`。

批准的档位如下：

| 档位词 | support_count 下界 | 唯一代表玩家最小数 |
|---|---:|---:|
| 绝大多数 / 普遍 | `ceil(N × 50%)` | 5 |
| 大量 / 很多 | `max(6, ceil(N × 20%))` | 5 |
| 不少 / 多名 | 5 | 3 |
| 部分 | 3 | 3 |
| 少数 / 个别 | 2 | 2 |
| 有玩家 / 有受访者 | 1 | 1 |

不同语义档位的可用 `support_count` 下界必须严格递增。极小样本下整数档位可能碰撞；代码按
“防夸大”的保守原则保留较弱表述，并把下界相等或倒置的更强档位标为“本题不可用”，模型
校验也必须拒绝该档位。例如 N=10 时，“绝大多数/普遍”不可用，不能靠模型自报数字伪造档位
差异。

跨题 `support_count` 禁止相加。跨题 finding 不生成总人数、比例或全局频次档位，只允许使用固定
口径“多道题均有提及”。如需精确跨题人数，必须另做逐条判定。

### 3.4 降级结构

阶段一产物版本为 `insight-findings-v1`。每题结构至少包含：

```json
{
  "question_key": "12",
  "scope_key": "12",
  "column_indexes": [12],
  "status": "complete | degraded | skipped",
  "respondent_count": 95,
  "findings": [],
  "degraded_source_ids": [],
  "failure": null,
  "diagnostics": {}
}
```

- `complete`：产出并通过契约校验。
- `degraded`：不保留未通过校验的 finding；`degraded_source_ids` 保存该题全部来源 ID。
- `skipped`：开放题没有有效回答。
- 阶段二对降级题按 ID 回填全部原文；阶段一不抽样、不截断、不静默丢弃。
- 指纹不符或 ID 不可解析时只阻断该题，并显式告警。

## 4. 阶段一执行规则

- 每道开放题一次逻辑调用，模型复用 `LLM_THEME_EXTRACT_*` 配置。
- 逐题并发默认 2，可在隔离试验中测 2、4、6。
- 每题首次调用后最多重试 2 次。
- 单次请求继续使用现有调用超时、协议切换、模型 fallback 和 JSON 修复。
- 输入超过保护阈值时该题降级，不把截断内容交给模型。
- 整个阶段默认超过 20 分钟只告警一次并继续，不设置生产硬截止。
- 仅隔离 CLI 显式传入 `--hard-timeout-seconds` 时允许试验硬截止；已完成题仍保存。

必须记录：

- 计划和实际逻辑调用数；
- 真实上游 HTTP 尝试数；
- 每题输入长度、模型、修复、错误、耗时和停止原因；
- token 用量及其是否完整；
- complete / degraded / skipped 数量；
- 阶段总耗时、并发和是否告警。

## 5. 阶段一 CLI

`scripts/replay_insight_report_v3_findings.py` 支持两条路径：

1. 自动路径：读取 XLSX，直接调用现有上传、列识别、列确认、方案规划、方案确认和统计 service，
   自动确认模型结果，然后运行阶段一。
2. 人工路径：复用用户在工作树服务中手动完成前四步的 session，仅运行阶段一。

两条路径必须写入同一个 `sess["insight_v3_findings"]` schema。每完成一题立即更新 session。
CLI 必须显式传 `--real` 才能调用真实模型；真实配置可用 `--env-file` 只读导入 `LLM_*`。

## 6. 后续阶段边界

阶段二负责：章节规划、按分析维度分章写作、固定背景与样本概况、核心发现汇总、统计附录、
正式 `survey_service` 接入、引擎开关和版本绑定。

阶段三负责：语义审校、未解决问题标注交付，以及追问时按需计算精确人数。

### 6.1 客观题统计必须走附录路径

V3 正文不生成旧引擎使用的 `## Part X` 标题，因此 V3 路径禁止调用
`stats_presentation.inject_qualitative_stats`。该函数按 Part 标题定位插入点；找不到标题时会跳过，
可能在不报错的情况下使逐题客观题统计完全缺失。

V3 必须复用后段已有的 `render_stats_appendix`，把逐题客观题统计作为附录追加到正文之后。
样本概况章只呈现总体样本结构和经筛选的画像表，不重复附录中的逐题统计。

### 6.2 引擎开关与版本绑定

- 新增 `INSIGHT_REPORT_V3_ENABLED`，默认值为 `True`。
- V3 版本快照必须保存 `report_engine = "insight_v3"`。
- 新生成的 `insight` 模式报告仅在开关启用时进入 V3；`quick` 与 `statistics` 始终保持原引擎。
- 历史报告重跑必须按版本快照中保存的 `report_engine` 选择引擎，机制复用
  `resolve_report_mode` / `report_mode` 的版本绑定方式。
- 关闭开关后，已保存为 `insight_v3` 的版本不得静默退回旧引擎；无法按原引擎重跑时必须明确失败并说明原因。

### 6.3 局部重做的预期降级

V3 snapshot 不保存 `analysis_artifacts`，因此现有局部重做能力会自动判定为不可用。这是阶段二的
预期降级，不得导致报告生成或历史查看失败。V3 必须提供明确的不可用原因，例如：

> 新版报告暂不支持局部重做，请整份重新生成。

禁止让 V3 落入默认空 `reason`。阶段二不实现 V3 局部重做，也不得伪造旧引擎所需的分析产物。

### 6.4 样本概况章体积上限

样本概况章的目标体积为本章合计 300—500 字和 2—3 张表。代码从 `structured_tables` 组装时，
只允许选取单维画像分布，以及少量与 `analysis_focus` 直接相关的表；其余统计表进入统计附录，
或不进入报告。不得把全部统计表复制到正文。

表格选择、数量限制和正文长度要求由代码确定性约束；模型不得自行扩大表格集合。样本概况章的
总体统计来自确定性 stats，不受观点级画像数字禁令限制，但不得与逐题统计附录重复。

### 6.5 SSE 进度阶段

V3 使用固定四阶段进度协议，`phase_total = 4`：

| phase | phase_index | 含义 |
|---|---:|---|
| `themes` | 1 | 阶段一逐题 findings 提炼；继续提供 `item_total` / `item_index` |
| `writing` | 2 | 章节规划、画像按需验证与正文写作 |
| `audit` | 3 | 阶段三审校；阶段二接入时允许明确标记为未启用或直通 |
| `finalize` | 4 | 复用现有后段完成统计附录、校验、保存和完成事件 |

`themes` 名称不得另造，以便复用前端现有逐项进度条。`finalize` 必须由复用的后段发出，V3
正文生成器不得重复发送最终完成事件。

### 6.6 snapshot 字段与接入红线

V3 版本 snapshot 按以下规则写入：

- `analyst_app = "insight_v3"`；
- `viewpoint_diagnostics` 保存新引擎自己的诊断，至少包含逐题成功/降级状态和各章重试次数；
- 不写 `analysis_artifacts`，以触发 6.3 的明确局部重做降级；
- `comparison_validation` 保持现有结构和行为，继续对最终 `full_report` 做确定性校验。

正式接入只允许在 `_full_report_stream` 的中段正文生成位置增加 V3 分支。其前段的版本解析、
生成锁、权限校验、历史重跑和统计准备必须保持逐行不变；后段继续负责附录、确定性校验、版本
保存和 `finalize`。交付时必须用定向 `git diff` 证明前段没有改动。

### 6.7 三层画像机制

画像在 V3 中只用于定性“告知”，不做交叉画像后的分类打分。只有 `profile_scope = "analysis"`
的画像维度参与以下计算；`profile_scope = "label"` 只保留在来源标注中。

第一层是零额外调用的存在性信息。代码只根据 finding 已绑定的代表性 `response_ids`，按
`respondent_ref` 去重后生成 `profile_presence`。该字段只表示“代表性提及者中包含这些画像取值”，
不表示比例、不排他、不能用于组间比较。模型只能据此写“提及者包括女性玩家和高段位玩家”一类
存在性表述。

第二层是按需人群专章。章节规划最多选择 2 个明确的画像取值；代码按
`source_registry[*].profile` 筛出该人群全部开放题原文，每个人群进行一次独立定性提炼。人群专章
可以归纳“该人群反馈中出现了哪些体验”，不得据此声称相对其他人群更集中，也不得输出画像占比。

第三层是按需差异验证。章节规划模型只可输出 `suspected_skew` 待验证标记，不得直接把差异论断
写进正文。待验证 finding 最多 5 个，并最多覆盖 3 次批量验证调用；验证模型只看 finding、回答
文本和本次调用短 ID，不得看到画像。代码把验证出的完整支持玩家集合与本题玩家画像构成比较，
只有通过阈值后才生成 `skewed_toward`。传给 writer 的 `skewed_toward` 只包含画像维度、取值和
支持玩家绝对人数，不包含百分比、占比、基线人数或 lift。

偏离判断使用可配置的保守默认值：本题已知画像玩家不少于 20、画像覆盖率不少于 80%、已知画像
支持玩家不少于 6、目标画像支持玩家不少于 4、目标画像在支持者中占比不少于 50%、相对本题
基线高至少 20 个百分点且 lift 不低于 1.5。所有百分比只存在于代码内部诊断，不进入模型上下文
或报告正文。映射或验证失败时字段为空并记录原因，报告继续生成。

Writer 使用硬门禁：没有对应 `skewed_toward` 时，拒绝“更突出”“更集中”“尤其明显”等比较性
表述；任何模型生成章节中的观点级画像百分比、比例和精确人数一律拒绝。代码生成的样本概况章
不受此限制。

### 6.8 阶段结果兼容指纹

若阶段二复用已完成的阶段一 findings，兼容性检查除 `file_sha256`、`plan_fingerprint` 和
`source_registry_fingerprint` 外，必须同时覆盖频次规则版本与 findings 提示词版本。任一维度缺失
或不一致时不得复用，必须重新运行阶段一，防止两套档位或提示词产物混用。

以下项目留待阶段三开工前另行确认：审校模型、审校问题的交付标记，以及追问时精确人数的计算协议。

## 7. 阶段一验收

1. 模型输出字段白名单不含任何原文字段；带 `quote` 的输出必须拒绝。
2. 同一玩家多条文本只获得一个模型短 ID。
3. 模型上下文不包含全局来源 ID 或玩家哈希。
4. 短 ID 经校验后才能翻译为全局来源 ID。
5. 单题失败时其他题继续，全部原文 ID 进入降级结构。
6. 非开放题不进入 questions；无有效回答的开放题才是 skipped。
7. 自动和人工前四步 session 进入阶段一后产生相同结构。
8. 三份批准的 XLSX 各完整运行一次；金币路固定题目子集先比较并发 2、4、6。
9. 随机抽取 5 个 finding，人工按唯一玩家核对 `support_count` 与原文实际条数的偏差，并写入交付报告。
10. 记录成功、失败和降级实际发生次数，不只报告成功路径。

只有 mock/静态测试通过时，阶段一真实语义质量仍为 NO-GO。真实模型回放和人工抽查完成后，
才能给出阶段一验收结论。
