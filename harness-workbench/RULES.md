# 代码改动规则（AI 行为约束）

本文件是所有参与此项目的协作者（包括 AI 助手和人类开发者）的行为准则。所有规则在任何对话、任何任务中无条件生效。

---

## 一、改动前必须确认

**在动任何代码文件之前，必须先向用户说明以下三点，得到明确同意后才能开始：**

1. 打算改哪个文件（精确到文件名）
2. 具体改什么（改的内容是什么）
3. 为什么要改（用户要求了什么）

没有用户的明确确认，不得修改任何代码文件，无论改动多小。

---

## 二、发现问题只报告，不擅自修改

在阅读或修改代码过程中，如果发现了用户没有提到的问题（bug、不一致、潜在风险、可优化之处），**只能告知用户，不能自行修改**。

正确做法：
> "我注意到 X 文件里有一处可能的问题：[描述]。需要我帮你修复吗？"

错误做法：顺手把它改掉，或者在完成主任务的同时附带修复它。

---

## 三、改动范围严格等于用户要求

用户说改 A，就只改 A。

不允许以下行为，即使理由听起来合理：
- "顺便把相关的 B 也改了"
- "A 和 C 是一起的，我把 C 也更新了"
- "这里原来的写法不太好，我顺手重构了一下"

**未经要求的任何改动，一律不做。**

---

## 四、一个目标可以有多个必要改动，但必须先说清楚

如果用户的一个目标需要同时修改多个文件，可以一次性完成这些必要改动，但必须在动手前先说明：

1. 涉及哪些文件
2. 每个文件分别改什么
3. 为什么这些文件都属于当前目标的必要范围
4. 改完后准备怎么验证

用户确认后，才能按这个范围执行。

执行过程中如果发现新的问题、新的优化点或额外风险，只能先报告，不能顺手纳入本次改动。

---

## 五、架构分层不能打破

本项目采用分层架构，层与层之间不能随意跳层调用：

- **routers/**：只负责接收 HTTP 请求、校验参数、调用 service、返回响应。不能在这里写业务逻辑或直接读写文件。
- **services/**：负责业务流程编排。调用 storage、integrations、core 工具库，不能直接操作 HTTP 响应格式。
- **storage/**：只负责读写 `data/` 目录下的本地数据文件，不负责业务流程判断。
- **core/**：放所有业务都可能用到的通用能力，例如配置、权限、解析、响应格式。不能反向依赖 routers 或 services。
- **integrations/**：只封装外部服务调用，例如 Dify、飞书。不能写具体业务流程。
- **schemas/**：只放请求、响应、数据结构定义，不写业务逻辑。
- **static/js/core/**：放前端通用能力，例如请求、SSE、工具函数。
- **static/js/features/**：放具体功能页面的交互逻辑。

新功能必须遵守这个分层，不能图省事把逻辑堆在 router 里，也不能让底层模块反向依赖上层模块。

后端分层相关改动完成后，应优先运行：

```bash
python scripts/check_boundaries.py
```

---

## 六、data/ 目录下的真实数据禁止删除、清空或覆盖

`data/` 目录存放的是运行时真实数据（历史报告、用户白名单、审计日志、登录状态、提示词、用户上传文件、标注结果等）。

**任何情况下不得删除、清空、覆盖或格式化这些文件和目录**，包括但不限于：

- `data/history.json`
- `data/whitelist.json`
- `data/audit_logs.json`
- `data/prompts.json`
- `data/app_settings.json`
- `data/ui_texts.json`
- `data/web_logins.json`
- `data/sessions/`
- `data/comment_uploads/`
- `data/annotate_results/`

如果某个任务确实需要操作这些文件，必须先单独说明：

1. 要操作哪个文件或目录
2. 会做什么操作
3. 是否会影响现有数据
4. 是否已经有备份或可恢复方案

经用户明确确认后才能进行。

---

## 七、启动服务或运行测试前，要注意是否会写入 data/

本项目的某些入口在启动或执行时可能会读写 `data/`，例如启动 FastAPI 应用时可能清理过期 session 文件。

因此，运行以下操作前，如果可能触发 `data/` 变更，必须先提醒用户：

- 启动后端服务
- 导入 `app.main`
- 跑会触发应用启动逻辑的测试
- 执行清理 session、写日志、写历史记录、写登录状态的脚本或接口

不能为了验证方便，擅自清理或改写运行时数据。

---

## 八、密钥和配置只走 .env + config.py

所有 API Key、外部服务地址、环境相关路径、业务阈值配置，只能通过 `.env` 文件 + `app/core/config.py` 统一读取。

不允许在任何代码文件中硬编码密钥、外部服务 URL、部署路径或敏感配置项。

内部前后端路由地址可以写在代码里，但应保持集中、清晰，不能散落成难以维护的魔法字符串。

---

## 九、不引入新的第三方依赖

不得在代码中 import 任何当前 `requirements.txt` 中不存在的第三方包。

如果确实需要新依赖，必须先向用户说明：

- 需要什么包
- 为什么需要
- 会带来什么影响

得到确认后，同步更新 `requirements.txt`，再写使用该包的代码。

---

## 十、修改部署敏感文件前必须单独提醒

以下文件的修改会直接影响服务器部署、启动、鉴权、外部服务连接或运行环境。修改前必须额外说明：

> 此修改会影响部署或运行环境。

部署敏感文件包括：

- `requirements.txt`
- `.env`
- `.env.example`
- `deploy.sh`
- `nginx-survey.conf`
- `server.py`
- `app/main.py`
- `app/core/config.py`
- `app/core/security.py`
- `app/integrations/dify_client.py`
- `app/integrations/feishu_client.py`

---

## 十一、改完必须说明验证方式

每次代码改动完成后，必须告诉用户已经做了哪些验证，以及结果是什么。

常见验证包括：

- 后端分层检查：`python scripts/check_boundaries.py`
- Python 语法检查：`python -m compileall app`
- 前端页面改动：浏览器或页面冒烟检查
- 接口改动：说明验证了哪个接口、输入是什么、结果是什么

如果没有运行验证，必须明确说明原因，不能假装已经验证。

---

## 十二、Git 操作必须由用户明确要求

不得主动执行以下 Git 操作，除非用户明确要求：

- `git commit`
- `git push`
- `git reset`
- `git checkout -- <file>`
- 删除、回滚或覆盖未确认的用户改动

查看状态、查看差异可以用于理解当前工作区，但不能擅自提交、重置或清理。

---

## 十三、密钥、隐私和日志不能泄露

不得在回复中直接展示以下内容：

- `.env` 原文
- API Key
- Cookie
- 登录 token
- 飞书授权信息
- 用户上传数据中的敏感原文

如果必须引用日志或配置内容，敏感字段必须打码，只保留足够定位问题的信息。

---

## 十四、依赖模型收敛的流程必须有工程门禁

凡是依赖模型执行压缩、筛选、去重、归并或逐轮收敛的流程，在修改前必须先写清：

1. 旧流程的硬约束和新流程的成功条件，特别检查两者是否不可同时成立。
2. 不同业务阶段是否允许遗漏输入、限制输出数量或返回空结果。语义不同的阶段不得因为
   JSON 结构相似而共用 prompt、validator 或成功条件。
3. 整个阶段的总耗时预算、预计逻辑调用数，以及无进展时立即停止的条件。不能只设置
   单次请求超时，也不能把失败或未压缩的候选原样投入下一轮。
4. 必须持久化的诊断：阶段耗时、逻辑调用数、真实上游尝试数、输入输出规模、压缩或筛选率、
   timeout/fallback、停止原因及最终有效产出。

高风险 LLM 流程在合入 `main` 前，除单元测试外还必须完成一份经过隐私审查的真实规模、
真实模型回放。没有回放时只能说明“静态验证通过”，GO/NO-GO 必须为 NO-GO。

算法、上下文优化、界面进度和诊断应按可独立验证、可独立回退的边界拆分提交；如果一个
提交包含多个风险不同的改动，必须在合入前拆开。详细门禁见 `docs/llm_pipeline_governance.md`。

---

## 十五、全项目任务分类、隔离开发、状态与清理约定

本节适用于整个 survey-web 项目的所有当前及未来任务、分支和独立工作树，不只适用于 BUG、
`codex/bugfix`、某条长期功能线或某个特定目录。

### 1. 自动分类与授权边界

用户不需要使用固定触发语。收到需求后，应根据实际目标主动判断任务类型，并先向用户报告
判断结果和依据：

- **BUG**：既有、已约定或原本应正常工作的行为报错、失效、结果错误、发生回归或明显偏离
  既定设计，使用 `codex/bugfix-<简短问题名>`。
- **新功能**：增加原先不存在的能力、入口、页面、设置、数据或业务规则，使用
  `codex/feature-<简短功能名>`。
- **优化**：现有功能能够工作，但需要改善性能、易用性、表达或维护方式；除非是在纠正既定
  行为，否则按新功能处理并使用 `codex/feature-<简短功能名>`。
- **混合任务**：同时包含独立 BUG 修复和新增能力时，默认拆成不同分支和工作树，分别验证、
  合入和回退；不得为了省事把不相关目标夹带在同一分支。

用户可以明确覆盖分类。分类清晰且用户已要求修改、实现或修复时，不需要用户另说分支名；
应先报告任务类型、建议分支、最新可确认的 `main` 基线、独立工作树和当前状态，再准备对应
环境。用户只要求诊断、解释、审计或状态报告时保持只读，不创建分支或修改文件。分类会实质
影响方案且无法可靠判断时，先只读核查并请用户决定。

准备分支和工作树不等于批准修改代码、提交、合入主干、推送或部署。修改文件前仍必须按第一
节说明精确文件、修改内容、原因、用户可见或部署影响和验证方式，并取得用户明确同意；到达
待合主干阶段后，也必须再次等待用户明确批准合入 `main`。

### 2. 分支、主干与工作树

开始涉及仓库文件修改的独立任务前，先盘点所有相关工作树、分支、远端引用、未提交改动和
最新可确认的 `main` 基线。不得覆盖其他任务的改动，也不得把缓存的远端引用或脏工作树假定
为最新、可丢弃状态。

`main` 只用于保存已验收成果、作为新任务基线以及执行合入后的交付验证，不得直接在 `main`
上开发。每个独立小功能或 BUG 默认使用一条对应的短期分支和一个独立工作树；当前任务已经
满足专用分支、正确基线和隔离工作树条件时可以复用，不得重复创建。

工作树负责目录隔离，分支负责承载提交。不得长期复用通用“小功能开发分支”或通用 bugfix
分支叠加多个无关任务。经用户明确指定的长期项目分支可以保留，但仍应按可独立验收、合入和
回退的里程碑控制范围，不能成为绕过 `main` 验证的第二主线。

独立工作树不等于运行时数据已经隔离。凡启动服务或运行可能写数据的测试，仍必须遵守第六、
第七节，并优先使用临时 `DATA_DIR` 等隔离配置，不得读写真实 `data/`。

### 3. 分类后的前置工作

BUG 修改前必须先复现或收集足够证据，区分可见症状、失败阶段、根因边界、数据或质量影响和
剩余未知项。不能把猜测当作根因，也不能因进入 BUG 分支而跳过修改审批。

新功能或优化修改前必须先明确目标、包含与不包含范围、用户可见行为、兼容性、验收标准和
必要文件边界。范围过大时，应拆成可独立验证和回退的小里程碑。

阅读过程中发现不属于当前目标的其他 BUG、风险或优化点，仍按第二、三节只报告，不得顺手
纳入当前分支。

### 4. 任务名称状态

当前任务名称最前面必须根据真实进度自动更新：

- `待开始`：正在盘点、分类、诊断或定义范围，尚未完成经批准的修改。
- `待测试`：经用户批准的修改已经完成，分支验证尚未完成。
- `待合主干`：分支验证通过，已报告合并条件，正在等待用户批准合入 `main`。
- `已合主干·待复验`：已经合入 `main`，但准确主干复验或安全清理仍未完成。
- `已合主干`：准确的 `main` 提交复验通过，临时工作树和分支也已安全清理。

如果真实状态不属于以上标准阶段，可增加准确的限定状态，例如 `待确认`、`NO-GO` 或
`待清理`；不得为了让标题看起来完成而提前推进状态。任务名称变化只用于报告进度，不表示
自动执行、自动测试、自动合并或代替任何用户确认。

### 5. 测试与合入主干

分支验证通过后，必须报告 GO/NO-GO、已完成与未包含范围、实际测试、未验证项、功能开关或
禁用界面行为、兼容性、共享文件风险、`data/` 风险、回滚方式和建议合入顺序，然后停在
`待合主干` 等待用户明确批准。

合并前必须重新刷新并核对 Git 状态，包括主工作树是否干净、远端和本地主干是否有新增提交、
祖先关系、ahead/behind、待合差异和其他任务的并发写入。预期快进时必须使用 `--ff-only`；
如果审计后 `main` 又发生变化，立即停止合并，把最新 `main` 同步回任务分支并重新验证。

合入后必须对准备交付或部署的准确 `main` 提交重新执行与风险相称的验证。分支上的测试结果
不能冒充主干复验结果；推送和部署仍是需要单独授权、单独报告结果的后续动作。

### 6. 工作树与分支清理

清理前必须确认任务提交已经安全进入 `main`，工作树不存在独有提交、未提交改动或未备份
内容，并检查 `.env`、忽略文件、`data/` 以及是否仍有其他任务或进程使用该目录。

涉及 `data/` 时必须遵守第六节：单独说明精确目录、影响和恢复方案，取得用户明确确认，完成
独立备份及逐文件校验后才能移除原工作树。不得用强制删除绕过未完成的安全检查。

条件全部满足后，才可移除临时工作树、删除已合并的本地任务分支，并在远端状态可核验时删除
本次创建的远端临时分支。任何一步不能确认时，保留相应内容并在任务名称中标明待处理状态，
不得宣称已经清理完成。本节不替代第十二节：实际执行提交、推送、删除分支或其他 Git 写操作
前，仍须有适用于当前任务和当前阶段的用户明确指令。

### 7. 其他任务同步

本规则进入 `main` 后，先向其他仍在旧分支上的 survey-web 任务发送项目级协调通知。协调通知
只要求记录并遵守本规则，不授权接收任务自行修改代码、切换分支、提交、合并或把 `main`
同步进其分支；任何实际同步仍须另获用户明确批准，并且不得覆盖该任务已有改动。
